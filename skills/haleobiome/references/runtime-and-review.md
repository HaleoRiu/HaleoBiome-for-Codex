# 运行模式与并行协议

## 宿主适配

使用当前环境实际暴露的工具及其文档，不硬编码某一产品版本或模型名。若有 spawn_agent/send_message/wait/interrupt 等能力，按其实际语义调度；若 API 名称不同，使用功能等价工具。不要为了角色分工自动新建用户侧任务，也不要注册模型或修改全局配置。

“后台运行”应有可查询状态、退出码和可取消的任务/进程标识。语言解释器启动成功不等于分析成功。缺少子代理或后台能力时按 SKILL.md 披露运行模式；缺少联网检索时说明证据核验限制，仍可整理已有可信文献。

## 版本与状态

在用户指定项目目录内，为每轮执行建立独立运行标识；每个模块按版本保存代码、参数、输入引用和结果。可使用 `runs/<run_id>/<module>/v1/`，或项目已有的等效结构。不把科研输入和产物写入安装的 Skill 目录。

输入大文件不必复制，但须记录绝对/项目相对路径、大小/版本或可行的校验值，并防止运行中被其他写入者修改；避免在未核验新旧输入一致时复用缓存。记录实际依赖版本和种子，而非把整个机器环境当作依赖。

运行状态示例：pending/running/succeeded/failed/cancelled/blocked。
审查状态示例：pending/in_review/passed/changes_required/unverified。
每条状态都带运行 ID、模块、版本、时间和证据位置。协调者写汇总状态；分析代码只由 Analyzer 写；审查者写各自意见文件，避免并发覆盖。

## Analyzer 与 Inspector

1. Analyzer 冻结可执行版本，向协调者提供代码/参数/输入清单、命令和日志路径。
2. 协调者安排 Analyzer 后台执行，同时将相同版本交 Inspector；不能先阻塞等待整个计算完成再启动审查。
3. Inspector 立即静态检查矩阵方向、ID 对齐、设计公式、变换/参数、依赖与输出路径；结果未就绪不是静态审查的阻塞项。
4. 发现问题即发送版本化反馈。至少记录：严重度（阻断/必须修复/建议）、位置、证据、影响、建议修复和复核方法；不要求提前猜出所有字段。
5. 协调者在计算期间处理反馈。阻断或结果必然失效时停止本次计算及已启动的受影响下游；建议可留待收敛后决定。若旧计算已结束，直接将其结果标为不可验收。
6. 中断 Agent 不一定终止其已启动的 shell 进程。通过记录的任务/进程句柄安全停止并确认退出，只操作本运行拥有的计算；不得按宽泛名称终止系统其他进程。
7. Analyzer 根据反馈创建新版本，再运行与复审；新旧代码、日志和结果各自保留。修订期间不覆盖运行版本。技术修复不重复确认；科学方案变化按原确认边界处理。

## 第二次并行及汇合

图可读取后，同时安排 Inspector 核对数值与 Visual Reviewer 读图。Supervisor 只在当前版本的运行、代码/数值审查及适用的视觉审查完成后给最终验收意见；任何未完成项须明示，不能用整体通过掩盖。

真实并行证据包含 run_start、inspector_start、feedback、run_end/stop 和各自的版本。希望证明“运行期间反馈”时，核验反馈时间早于对应运行结束；短任务若计算先结束，只能证明启动安排有重叠或审查晚于结束，不能虚构时间线或故意拖延科研计算以营造并行。
